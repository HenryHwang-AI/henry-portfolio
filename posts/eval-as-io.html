评测与追溯为什么也是 I/O 问题 Why eval and citation are also an I/O problem

读 FlashAttention 一类工作，最打动我的不是具体 kernel 写法（我也没假装写过 Triton 教程），而是那句直觉：瓶颈常常在搬运，不在算力。标准 attention 会物化巨大中间矩阵，在慢速大内存里进进出出；好的设计改成分块、在快速小缓存里算完该算的，再只把必要结果写回。

映射到 Agent 产品

评测台很容易犯同样的错：每次回归都把完整对话轨迹、全量工具日志、每一轮 prompt 全部落盘「以防万一」。磁盘和人工阅读带宽变成 HBM；真正决定「好不好用」的信号——任务是否完成、引用是否对上、脆弱 GUI 路径是否被踩到——反而淹没在中间物里。引溯 RAG 也一样：把整库塞进上下文，等于物化一张用不上的大表；更好的是只把需要的块取进「工作集」，并在答案旁保留可点的出处。

诚实边界

这是产品 / 系统思维上的类比，不是内核实现指南。我没有在这里教 tiling 或 online softmax。我借的是纪律：别默认物化巨大中间态；缓存真正反复用的信号；I/O 预算和正确性一样要设计。 作战室、评测台、引溯三个 Demo，都在逼我问——这一步是在算，还是在无意义地搬？

工作集里放什么

我给评测台定了一个粗糙预算：单次回归，人眼只应扫一张「失败摘要卡」——任务 ID、失败类型、是否踩 GUI 逃生舱、关键引用是否缺失。完整轨迹默认进冷存储，按需拉取。引溯侧同理：检索 top-k 片段进上下文，答案只绑定用过的片段 ID；全库扫描留在索引层，不进每一次生成的热路径。

一旦发现自己在为「也许以后要看」而默认全量物化，就当作一次 I/O 回归缺陷来修。Agent 产品的延迟与成本，很多时候不是模型更大，而是中间态太贪。

What stuck from FlashAttention-style work isn’t a kernel walkthrough (I’m not pretending I shipped a Triton tutorial)—it’s the intuition that the bottleneck is often movement, not FLOPs. Naive attention materializes a huge intermediate and shuttles it through slow bulk memory; better designs tile, finish the needed math in a fast small cache, and write back only what must persist.

Mapped onto agent products

Eval labs make the same mistake: every regression dumps full transcripts, tool logs, and every prompt “just in case.” Disk and human reading bandwidth become HBM; the signals that decide “usable”—task done, citations aligned, fragile GUI paths hit—drown in intermediates. Citation RAG mirrors it: stuffing the whole corpus into context materializes a useless giant table; better to fetch only the working set and keep clickable sources beside the answer.

Honest boundary

This is a product/systems metaphor, not a kernel guide. I’m not teaching tiling or online softmax here. I’m borrowing the discipline: don’t default to materializing huge intermediates; cache the signals you reuse; budget I/O like correctness. The war room, eval lab, and citation demos all force the same question—are we computing, or just shipping bytes around?

What belongs in the working set

I set a rough eval budget: each regression, human eyes should scan one failure summary card—task id, failure type, GUI hatch hit or not, missing key citations. Full traces stay cold and pull on demand. Citation side matches: retrieve top-k into context; bind answers only to used chunk ids; full-corpus scans stay in the index, out of every hot generation path.

Whenever I default to materializing everything “in case we need it later,” I treat it as an I/O regression bug. Agent product latency and cost often aren’t “model too small”—they’re intermediates that got greedy.
