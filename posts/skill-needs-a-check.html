把 SOP 收成 Skill 之后，怎么验收它学对了 After an SOP becomes a skill, how do you check it learned

把运营 SOP 封进技能包，是为了按同一套标准稳定产出，不是为了演示系统会操作。上线以后要验收的，是技能的边界，以及它怎样被反馈改掉。记下一次操作，和学会一条规则，不是同一件事。

技能包按矩阵来排，不按一次演示来排

AllyNext 把运营 SOP 拆成 Skills，并规划 Skill 和 Agent 的能力矩阵。取数走 Function Calling 和 MCP，Memory 保存上下文。整条链路是「数据驱动生成 → 结果校验 → 交付」。搜索量、竞争度、爆款结构和 COSMO 用户意图写进 Prompt。输出是结构化的：Listing 的标题和五点，脚本的钩子、口播和分镜，以及视频提示词，并附上修改理由。人能看见改了什么、为什么改。

时间是 2025 年 3 月到 12 月。项目条目写 AI 产品负责人，工作经历写深度参与全链路。我两处都保留，避免把参与写成另一套职权。案例在 AllyNext。

学对了，要看反馈有没有回到技能

验收走的是「Badcase → 教训 → 技能 / 记忆更新」。人在回路里，人工反馈就是信号。一次采纳率从 [30–50%] 到 [70–85%]，区间保留。这个区间说明：生成结果里，能被直接收下的比例在上升，同时仍然有一部分要退回去改技能或改记忆。修改理由跟着结构化结果一起交出来，是为了让退回的那一部分说得清，而不是只给一个通过或驳回。

按风险划分的自动执行和人工确认还在。关键决策强制人确认。取回真实结果才算交付，成品和过程产物分开。技能包因此不是一条放完就结束的脚本，它要经过校验，才进入交付。

四类场景都要能按同一套标准退回

技能要撑住的是已经上线的四类生产：Listing 文案、A+ 视觉、爆款脚本，以及 AI 视频提示词和视频生成。运营场景覆盖 80% 以上，覆盖口径没有再定义，它只说明这些场景铺开了。一次采纳率的区间才靠近「学对了没有」：直接能留下的比例从 [30–50%] 到 [70–85%]。退回的那一部分，要能写成教训，再写进技能或记忆。修改理由附在结构化结果上，是为了让退回指向标题、五点、钩子、口播、分镜或提示词中的某一项，而不是整包重来却说不清改哪。

Function Calling 和 MCP 解决的是技能取数，避免模型凭空补搜索量、竞争度或爆款结构。Memory 保存的是这条链路的上下文，更新仍走 Badcase 到教训再到技能或记忆。我能核对的是矩阵、取数、记忆、校验和这个采纳区间。商舟的选品节点仍按 Workflow、Agent 决策和人工确认来写，不在这篇文章里改称为 Skills。

验收因此看三件事是否同时在：技能有没有按矩阵覆盖到四类场景，取数有没有走调用而不是凭空写，退回的结果有没有变成教训并写回技能或记忆。一次采纳率上升，说明直接可用的比例变了；区间还在，说明我不用一个单点宣布「已经学会」。人工反馈是这条闭环的信号，关键决策仍要人确认。技能包装上线，只是这三件事的起点。覆盖率说明场景铺开了，采纳区间说明直接能留下的比例，两者都要在，我才把「SOP 被收成技能」写成已经能验收。

Packing an operations SOP into a skill pack is for stable output against one standard. It is not a demo that the system can click around. After launch, what has to be checked is the skill’s boundary, and how feedback changes it. Remembering one operation and learning a rule are not the same thing.

The pack is planned as a matrix, not as one demo

AllyNext split operations SOPs into skills and planned a skill-and-agent matrix. Data comes through function calling and MCP. Memory keeps context. The chain is data-driven generation, then a result check, then delivery. Search volume, competition, the structure of hit products, and COSMO user intent go into the prompt. The output is structured: Listing title and five bullets, script hook, voiceover and shots, and video prompts, each with a reason for the change. A person can see what changed and why.

The dates are March to December 2025. The project entry says AI product owner; the work history says deep participation across the chain. I keep both, so participation is not rewritten as a different authority. The case is AllyNext.

It has learned when feedback returns to the skill

The check is bad case, then lesson, then an update to the skill or the memory. A person stays in the loop, and human feedback is the signal. First-pass acceptance moved from [30–50%] to [70–85%]. I keep the ranges. They say the share of results that can be taken as-is is rising, and that a remainder still goes back to change the skill or the memory. The reason for a change ships with the structured result, so the returned part can be named, rather than ending as a bare pass or reject.

Automatic steps and human confirmation, split by risk, remain. Critical decisions require a person. Delivery means a real result came back. Finished goods and intermediate artifacts stay separate. The skill pack is therefore not a script that ends when it is stored. It passes a check before it counts as delivered.

All four scenes have to be returnable against one standard

The skills have to hold the four production types already shipped: Listing copy, A+ visuals, hit-product scripts, and AI video prompts plus video generation. Operations-scene coverage of 80%+ is not further defined. It only says those scenes were laid out. The first-pass range is what sits closer to “did it learn”: the share that can be kept as-is moved from [30–50%] to [70–85%]. The part that comes back has to be writable as a lesson, then written into the skill or the memory. A reason attached to the structured result lets the return point at the title, the five bullets, the hook, the voiceover, the shots, or the prompt, rather than redoing the whole pack without saying what changed.

Function calling and MCP are how a skill fetches data, so the model does not fill in search volume, competition, or hit-product structure from nothing. Memory keeps context for the chain. Updates still run from bad case to lesson to skill or memory. What I can check is the matrix, the fetch, memory, the check, and that acceptance range. Shangzhou’s selection nodes stay written as workflow, agent decision, and human confirmation. I do not rename them skills in this essay.

The check therefore looks at whether three things are present together: the skills cover the four scenes through the matrix, data comes through a call rather than being written from nothing, and a returned result becomes a lesson written back into the skill or the memory. A rising first-pass rate says the share that can be used as-is changed. The range remains, so I do not announce “it has learned” from a single point. Human feedback is the signal in this loop, and critical decisions still need a person. Shipping the skill pack is only the start of those three checks. Coverage says the scenes were laid out. The acceptance range says what share can be kept as-is. I treat “the SOP has been gathered into a skill” as checkable only when both are present.
